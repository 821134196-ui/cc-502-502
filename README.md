# 可循环周转箱押金管理（toteflow）

工厂发货时把可循环周转箱分配给客户，按**箱型、箱号、押金、出库批次**逐箱记账；
客户返箱后检查**箱体、封盖、标签**，合格箱重新入库，破损箱送维修或报废。
SQLite 保存逐箱事件，破损照片本地存储，财务回执走模拟适配器，纯标准库实现。

## 一条本地命令启动

```bash
./run.sh            # 初始化库 + 混批返箱样例 + 启动 http://127.0.0.1:8000
./run.sh 8200       # 指定端口
./run.sh --reset    # 重建演示数据
# 等价于：python3 -m toteflow --reset --port 8000
```

## 页面

- **客户箱账** `/accounts`：按客户汇总累计发箱 / 应返 / 实返 / 待修 / 报废与押金余额，可展开到箱号
- **发箱扫描** `/dispatch`：箱号 + 箱型 + 出库批次 + 客户，发箱即记一笔押金收取
- **返箱验收** `/returns`：应返 / 实返 / 待修同屏看板；扫描预检归属与批次，三项质检 + 维修费 + 破损照片；**折抵金额紧挨验收结论**展示
- **维修池** `/repair`：破损箱送修，修完重新入库并结清押金尾款，或转报废
- **逾期清单** `/overdue`：超过应返日 30 天未返还，财务可核销并扣抵押金
- **押金流水** `/ledger`：逐笔收/退/扣，财务复核通过后生成模拟回执，驳回自动挂争议

## 业务规则与异常处置

| 场景 | 处置 |
|---|---|
| 返还数量不足 | 客户箱账「应返」恒大于「实返+待修+报废」，逐箱可追溯 |
| 箱号不属于该客户 | 预检与提交均拒绝（422），箱子保持在外、不产生任何流水 |
| 跨批次（混批）返还 | 仓库扫描被拦截并留痕；仅主管确认后按**实际出库批次**入账 |
| 重复退箱 | 条件更新 `WHERE state='out'` + `BEGIN IMMEDIATE`，并发下恰好一次成功 |
| 押金争议 | 财务开争议后该箱冻结抵扣（423），解决后才能验收结算 |
| 维修费用 | 从押金折抵（封顶 ¥80），维修完成按实际费用多退少补；无修复价值则报废 |
| 长期未返 | 逾期清单跟进；确认追不回时财务核销，押金全额扣抵 |
| 财务复核 | 退还/扣减一律先「待审」，复核通过才生效并给回执；驳回必填原因并挂争议 |

## 一致性设计

- **同一箱号绑定**：返箱验收与押金抵扣写在同一个数据库事务，`returns.refund_id/deduct_id`
  回指流水，押金守恒「收取 = 退还 + 扣减」有测试兜底。
- **并发安全**：每笔写事务 `BEGIN IMMEDIATE` 立即取写锁，状态迁移用条件 UPDATE，
  8 线程并发退同一箱只有 1 笔成功（`tests/test_domain.py::test_concurrent_duplicate_return`）。
- **职责分离**：仓库只改实物状态，写不出押金流水；财务不碰验收。角色在服务层强校验，HTTP 越权返回 403。
- **审计轨迹**：`box_events` 为 append-only 逐箱事件流；押金流水不可变，冲正以新行/复核状态表达。

## 目录

```
toteflow/
  config.py    押金标准、逾期天数、账号
  db.py        SQLite schema、事务与事件
  services.py  领域服务（发箱/验收/维修/争议/复核/核销）
  queries.py   箱账、看板、逾期、维修池、流水查询
  adapters.py  财务回执（MockFinanceAdapter，同协议可换真实接口）
  photos.py    破损照片本地存储（data/photos/<箱号>/）
  web.py       stdlib HTTP + 会话 + 六个页面
  seed.py      演示数据（含混批返箱）
data/          SQLite 库与照片（运行时生成，已 gitignore）
```
